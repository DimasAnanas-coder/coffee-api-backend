| 1. Модели и репозитории | Выполнен | Связанные ORM-модели, нужные поля, репозитории и Unit of Work используют одну внедрённую сессию. |

| 5. Исправление N+1 | Выполнен | Выполнен и записан сравнительный эксперимент. В приложении нет плохого сценария, который загружает пользователей и затем обходит `user.orders`, поэтому оптимизация такого сценария не добавлена в API. |


## Модели, репозитории и Unit of Work

`User` содержит `id`, необязательное `name`, уникальный обязательный `email` и обязательный `balance`. Связь `User.orders` настроена через `relationship`. У `Order` есть обязательные `user_id` и `amount`, поле `status` с `nullable=False` и серверным значением `pending`, а также обратная связь `Order.user`.

`UserRepository` предоставляет создание, поиск по email и ID, обновление, удаление и список пользователей. `OrderRepository` предоставляет создание, поиск, обновление, удаление и список заказов. Репозитории получают сессию при создании и не вызывают `commit()` или `rollback()`.

Use case зависят от `UnitOfWorkProtocol` из `app/ports.py`. Реализация `SqlAlchemyUnitOfWork` находится в `app/infrastructure/unit_of_work.py` и предоставляет `uow.users` и `uow.orders` на общей сессии. Успешный выход из `with uow:` фиксирует транзакцию, исключение откатывает её.

`CreateOrderUseCase` проверяет положительность суммы, блокирует строку пользователя через `get_by_id_for_update`, проверяет наличие пользователя и баланс, списывает сумму и добавляет заказ. При этом для PostgreSQL блокировка строки снижает риск конкурентного перерасхода одним пользователем; сама атомарность двух операций такую конкуренцию не решает.

## Миграции и проверка API

Начальная миграция `6b06907d4a39_create_users_and_orders.py` создаёт таблицы `users` и `orders`, первичные ключи, внешний ключ `orders.user_id -> users.id`, уникальность email и типы колонок. В неё уже включён `orders.status` с `nullable=False` и `server_default='pending'`.

Следующая миграция `b7c42e1a9d03_add_name_to_users.py` добавляет nullable-колонку `users.name`. Она допускает строки, созданные до миграции. Проверка выполнена на отдельной временной SQLite-базе, а не на настроенной PostgreSQL-базе проекта:

1. `alembic upgrade head` создал таблицы и добавил `users.name`.
2. Через API созданы пользователь и заказ: ответы `201`; заказ получил `pending`, баланс изменился с `100.00` на `75.00` после заказа на `25.00`.
3. `alembic downgrade 6b06907d4a39` удалил `users.name`; `orders.status` остался, потому что он находится в начальной миграции.
4. Повторный `alembic upgrade head` вернул колонку `name`, но прежнее значение имени стало `NULL`.

Таким образом, downgrade миграции `name` удаляет значения этого столбца, и повторный upgrade не может их восстановить. Это не проверка требуемого рубрикатором downgrade для `orders.status`: отдельной миграции статуса в текущей истории нет. Если откатить базу дальше начальной ревизии, начальная миграция удалит обе таблицы вместе с данными.

Alembic загружает настройки из `DATABASE_URL`. Команды из корня проекта:

```powershell
# Применить все миграции до текущей головы
python -m alembic upgrade head

# Откатить одну последнюю миграцию
python -m alembic downgrade -1

# Вернуться к ревизии до добавления users.name
python -m alembic downgrade 6b06907d4a39
```

Перед запуском укажите доступный PostgreSQL в `.env`. На рабочей базе перед downgrade следует учитывать потерю данных удаляемых колонок.

`alembic/env.py` импортирует `Base`, `Order` и `User` из `app.infrastructure.models` до `context.configure`. Импорт моделей регистрирует их в `Base.metadata`. Autogenerate помогает подготовить миграцию, но не заменяет ручную проверку изменений данных и downgrade.

## Граница транзакции и injected failure

Граница создания заказа находится в `CreateOrderUseCase`: списание баланса и вставка заказа выполняются внутри одного `with uow:`. Ошибка до успешного выхода из блока приводит к rollback обеих операций.

**Тест с намеренной ошибкой после списания и проверкой из новой сессии в проекте отсутствует.** Его прежняя версия была удалена; по решению автора тесты добавлять не будем. Поэтому атомарность подтверждена реализацией и обычным API-сценарием, но требуемый рубрикатором failure-сценарий не проверен. Для полного критерия тест должен подменить добавление заказа так, чтобы оно выбросило исключение после `set_balance`, а затем новой сессией проверить старый баланс и отсутствие заказа.

## Замер N+1

Проведён отдельный диагностический эксперимент на временной SQLite-базе с четырьмя пользователями, у каждого был один заказ. Для каждого варианта создавалась новая `Session`; счётчик `before_cursor_execute` очищался перед чтением.

| Вариант | Число SQL-запросов | Наблюдение |
| --- | ---: | --- |
| Наивный `select(User)` и затем обход `user.orders` | 5 (`1 + 4`) | Один запрос пользователей и четыре отдельных `SELECT ... FROM orders WHERE ? = orders.user_id`. |
| `select(User).options(selectinload(User.orders))` | 2 | Запрос пользователей и один запрос заказов с `WHERE orders.user_id IN (?, ?, ?, ?)`. |

Замер подтверждает разницу между ленивой загрузкой и пакетной загрузкой. Это демонстрационный сценарий: текущие пользовательские endpoints возвращают поля пользователя и не обходят `user.orders`, поэтому в существующем API такой N+1 путь не найден.

## Дополнительное диагностическое ревью

### 1. Ошибка `flush()` и rollback

**Дефект:** исключение после неудачного `flush()` перехватывается, но транзакция не откатывается. **Инвариант:** после ошибки сессия не должна продолжать работу в неудачной транзакции. **Последствие:** последующий `commit()` может вызвать `PendingRollbackError`, а предыдущие изменения не должны считаться сохранёнными. **Исправление:** вызвать `rollback()` перед продолжением работы или завершить блок `with session.begin()`. `close()` закрывает текущую единицу работы и откатывает незавершённую транзакцию, но сам по себе не означает, что объект `Session` навсегда нельзя использовать повторно. **Проверка:** после rollback выполнить новую вставку, commit и прочитать её новой сессией.

### 2. Два commit при создании заказа

**Дефект:** баланс фиксируется до вставки заказа, для которой затем выполняется второй commit. **Инвариант:** списание и заказ должны сохраняться вместе. **Последствие:** если вставка заказа упадёт, баланс уже останется уменьшенным. **Исправление:** выполнить обе операции в одной транзакции UoW. **Проверка:** вызвать ошибку между операциями и проверить баланс и отсутствие заказа новой сессией. Одна транзакция сама по себе не предотвращает конкурентный перерасход; текущий use case дополнительно блокирует строку пользователя через `FOR UPDATE` на базах, которые поддерживают такую блокировку.

### 3. Граница репозитория и Unit of Work

**Дефект:** `OrderRepository.add()` делает commit, а use case позднее вызывает rollback; кроме того, отсутствуют проверки суммы, пользователя и баланса. **Инвариант:** репозитории выполняют операции с общей внедрённой сессией, а прикладной сценарий владеет общей транзакцией и бизнес-проверками. **Последствие:** commit внутри репозитория делает последующий rollback неэффективным и не позволяет атомарно менять несколько таблиц. **Исправление:** использовать `UnitOfWorkProtocol` и репозитории `uow.users`/`uow.orders`, как в текущем проекте. **Проверка:** проверить, что ни один репозиторий не вызывает commit/rollback; сценарий создания заказа должен проверить сумму, пользователя и баланс до фиксации.

### 4. Ошибки Alembic-миграции

**Дефект:** добавление `orders.status` как `NOT NULL` без серверного default не заполнит старые строки; downgrade удаляет `users.status` вместо `orders.status`. **Инвариант:** миграция должна изменять правильную таблицу и оставлять допустимое значение в каждой существующей строке. **Последствие:** upgrade может упасть на непустой таблице, а downgrade завершится ошибкой или затронет неверную схему. **Исправление:** добавить `orders.status` с серверным значением `pending` или выполнить поэтапное добавление, заполнение старых строк и установку `NOT NULL`; в downgrade удалить колонку `orders.status`. Импортировать модели до `context.configure`, а autogenerate считать черновиком. **Проверка:** применить миграцию на базе с заказами, проверить `pending`, выполнить downgrade и повторный upgrade. Удаление колонки необратимо удаляет её прежние значения; повторный upgrade восстановит для строк только `pending`.

### 5. N+1 при чтении заказов пользователя

**Дефект:** цикл читает `user.orders` при ленивой загрузке. **Инвариант:** число запросов не должно расти на один для каждого пользователя. **Последствие:** для N пользователей получится примерно `1 + N` запросов. **Исправление:** использовать `selectinload(User.orders)` или эквивалентную пакетную загрузку. **Проверка:** сравнить SQL-счётчики для свежих сессий. В выполненном эксперименте получено 5 запросов наивно и 2 с `selectinload`, второй запрос пакетно фильтровался через `IN`.
